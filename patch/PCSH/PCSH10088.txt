# Super Robot Wars X [ASIA]
#
# B.B.Studio "Kuro" engine (the same code base as Super Robot Wars V, PCSH10001),
# with the AImpact 2D library and an srlib/SampleUtil layer that nothing in this build
# calls directly (a virtual path into it exists - see @MSAA below). Everything is in
# the main module; no user suprx is loaded.
#
# Native state (static analysis; the dump was taken before the game called anything,
# so it has no runtime records and no polled framebuffer):
#   display  960x544, pitch 1024, 3 x 3 MiB CDRAM buffers, S8D24 depth in main RAM
#            (USER_RW_UNCACHE, 0x1FE000, stride 960), MSAA off;
#   internal the frame is rendered into one 1920x1088 off-screen atlas in CDRAM and
#            the composite is upscaled to the display. The rectangle used inside the
#            atlas is picked from an 8-row table in seg1 by a "quality level" k;
#            this build uses k = 1 (720x408) for the frame and k = 0 (960x544) for
#            the screen-capture/cross-fade path. setQuality(6) and setQuality(5) are
#            also called (0:0x6FFEA, 0:0x6FFF2) from a caller whose reachability is
#            not established; @IB rewrites all eight rows, so it holds for any k.
#
# What is in this file: 109 lines - 20 @FB, 32 @IB, 57 @MSAA. No @FPS section.
#
# @FB   (960x544 / 720x408 / 640x368 / 480x272) moves the display buffers and
#       everything stated in device pixels: sceDisplaySetFrameBuf, the display render
#       target, the colour surfaces, the display buffers bound as textures, all four
#       SceCommonDialogUpdateParam render targets (two of them in unreferenced code)
#       and the two hard-coded full-screen region clips (both unreferenced, patched so
#       that no 959/543 is left behind). The pitch stays 1024 and the depth buffer
#       stays 960-stride / 0x1FE000 (both legal for every smaller size), so no
#       allocation changes. Nothing else moves: the engine's 2D/UI/text/cut-in geometry
#       is stated in a logical 960x544, 1280x720 or 1920x1080 canvas that ends in NDC,
#       and NDC covers the patched colour surface. No touch library is imported.
#       At 960x544 every @FB line reproduces the stock bytes: it is a byte-identical
#       no-op at the native setting.
# @IB   rewrites the atlas rectangle table so every quality level renders at the
#       selected size instead of the engine's own 960/720/640/480/360 ladder.
#       NOT a no-op at the native internal size: at ib = 720x408 the active row k = 1
#       comes out byte-identical, but row k = 0 - the capture/cross-fade path, which is
#       reachable - drops from 960x544 to 720x408, and the six unreachable rows change
#       too. No @IB value leaves the whole table unchanged, because the eight rows hold
#       five different ladder steps. At ib = 960x544 rows 0 and 5-7 are byte-identical
#       and rows 1-4 become 960x544, i.e. the game renders at the full display size.
#       Leaving row 0 (1:0x8298/0x82A8/0x82B8/0x82C8) unpatched would make ib = 720x408
#       a true no-op and keep transition backdrops at display size at every setting;
#       uniformity was preferred, so that "internal resolution" means one number for
#       everything the game renders and a capture cannot cost more fill than the frame
#       it is captured from. That is a policy choice, not a constraint - see the report.
#       Known limit: the atlas stays 1920x1088, so an @IB above 960x544 is clamped to
#       960x544 (a larger rectangle would leave its quadrant).
# @MSAA (2x / 4x) gives the display target, the off-screen atlas, the unreferenced second
#       1920x1088 target 0:0x63132 and all 37 fragment programs one common multisample mode;
#       the depth buffers and strides are scaled with it. Tested on hardware: 2x renders
#       (a GXM trace showed every scene and draw succeeding, no program/target mismatch),
#       and 4x with @IB set runs through boot and the terms-of-service screen.
#       Why the earlier builds were black: the engine's main shader patcher (0:0x4D85A) gets
#       fixed 64 KiB buffer / vertex-USSE / fragment-USSE pools and no grow callbacks, and X
#       builds ~250 fragment programs into it (18 material classes x 14 blend slots; V has
#       17 x 13). Measured at 2x, they need 65,584 bytes of fragment USSE - 48 bytes over
#       64 KiB - so the last programs failed to build and nothing was drawn. The six lines
#       0:0x4D712..0:0x4D7FA double all three pools to 128 KiB at 2x/4x (+192 KiB of main
#       RAM); at none they emit the stock 64 KiB.
#       MEMORY: at 2x the atlas depth grows to 16 MiB (32 MiB at 4x). Left in main RAM it
#       made a later allocation fail at 2x (the engine's wrapper retried it in CDRAM), so
#       0:0x5F31E moves the atlas depth to the video pool at 2x/4x, as SRW V does. That
#       leaves main RAM below the stock game's use at every setting.
#       srlib's own render target (0:0x25BFE) is left at its caller's mode, as in SRW V;
#       nothing observed creates it. srlib's four alternate-mode program variants
#       (0:0x240B6, 0:0x240DE, 0:0x2413E, 0:0x24166) are switched with the rest, which at
#       none builds them at mode 0 instead of 1/2 - the only change at none besides the
#       display-depth allocation-failure branch 0:0x4D6AC/0:0x4D6BE (map length follows the
#       fallback size). Every other line emits the stock value at none.
#       Known limit, shared with SRW V: GXM rejects one material program at 2x/4x
#       (SCE_GXM_ERROR_INVALID_VALUE at 0:0x722FE) - a depth/stencil-only shader with no
#       colour output (seg1:0x2288, identical in V). Nothing bound it during the traced run;
#       if a scene uses it, that pass is skipped at 2x/4x.
# @FPS is not provided. The pacing itself is patchable - g_vblank (1:0x7308) has ten
#       writers, all immediates 1 or 2 - but a 60 FPS battle would need a half-rate call
#       hook, and the one prototyped for the Trails ports was withdrawn from the plugin.
#       The evidence is missing too: menus and map are frame-locked at 60 and battles at 30
#       with no timestep constant, so a cap halves logic speed and an unlock doubles it,
#       and neither the demo step 0:0x11F0E8 nor the menu/map update was shown to
#       tolerate being divided. See the report; the section is explicit about what is
#       measured and what is inherited from the previous pass.
#
# Offsets are for module NID 0xF521B359 only.
