# Super Robot Wars V [ASIA]
#
# B.B. Studio "Kuro" engine (+ srlib 1.1), module VITA / eboot.bin, NID 0x373CE5C7.
# Native state: 960x544 display, 3 CDRAM display buffers (pitch 1024 px), depth S8D24
# tiled stride 960, 60 Hz frame-locked (vblank count 1).  MSAA is off on both render
# targets; of the 36 sceGxmShaderPatcherCreateFragmentProgram sites, 32 pass mode 0 and
# 4 are srlib's alternate 2x/4x variants of two programs (modes 1 and 2).
#
# @FB  lowers the display resolution and the composite destination.  The scene itself
#      is NOT drawn into the display buffers - it goes into a rect of the off-screen
#      1920x1088 atlas (see @IB) and is blitted back by the composite quad, which
#      reaches the GPU in NDC -1..+1 and therefore follows whatever surface is bound.
#      All game geometry likewise reaches the GPU already in clip space (the engine
#      divides device pixels by the constant 960/544 and never queries the surface),
#      so no UI, layout or scaler constant is touched and the picture scales as a
#      whole - but @FB lowers the display/composite cost only, not the scene's fill
#      cost.  Use @IB for that.  The 1920x1088 atlas allocation itself stays at stock
#      size at every @FB setting.
# @IB  lowers the internal resolution: every frame is drawn into a rectangle of the
#      off-screen 1920x1088 atlas (frame start 0:0x440CC -> 0:0x6588C -> bindTarget(0,
#      force) at 0:0x658BE, sceGxmBeginScene at 0:0x61434, region clip/viewport from
#      rect[k][0] at 0:0x658F2 -> 0:0x6114C) and the composite 0:0x65A56 ends that
#      scene at 0:0x65AB0, begins the display scene at 0:0x65AFC and draws the atlas
#      rect over an NDC -1..+1 quad, UVs from the same rect (0:0x60A0E).  Stock k = 1
#      (1:0x5AE0 = 1, applied every frame at 0:0x440E0), i.e. 720x408 upscaled to
#      960x544 already.  The block rewrites only the w/h halves of the rectangle
#      table at seg1 0x7364 (8 quality rows x 4 rects x {x,y,w,h} f32); the quadrant
#      origins {0,960} x {0,544} are untouched and min(ib_w,960)/min(ib_h,544) is the
#      exact quadrant size, so no rect can leave its quadrant.  Each rect keeps its
#      ratio to the largest of its own row.  Row 0 is reachable from the cross-fade /
#      screen-capture helper 0:0x269094 (setQuality(0) at 0:0x2690E0, conditional on
#      the display being the bound target), so below native a transition backdrop is
#      captured at @IB size too.  Battle state 2 calls setRenderMode(-1) (0:0x120588)
#      and draws to the display directly: that is NOT affected by @IB.
# @MSAA gives the choice of 2x/4x on the display target and the one off-screen
#      render-to-texture target.  All 36 sceGxmShaderPatcherCreateFragmentProgram
#      sites are switched with it, including srlib's four alternate-slot programs, so
#      whichever slot srlib's selector picks the program matches the target: the
#      module's only six sceGxmBeginScene sites (0:0x4D3D0, 0:0x61312, 0:0x61350,
#      0:0x613F4, 0:0x61434, 0:0x65AFC) all bind a Kuro target, and both Kuro targets
#      are switched here.
#      MEMORY: the two depth buffers are the only allocations that grow - the
#      1920x1088 atlas depth by +24.0 MiB at 4x and the display depth by +6.0 MiB,
#      both out of the 256 MiB main partition.  A static budget of every
#      sceKernelAllocMemBlock in the module puts it at 218.1 MiB at none, 228.0 at 2x
#      and 248.0 at 4x, and neither the depth allocation nor sceGxmCreateRenderTarget
#      checks its return value, so 8 MiB is not a margin to ship a never-tested
#      setting on.  0:0x5E646 therefore moves the atlas depth into the video pool at
#      2x and 4x: it rewrites the allocation type 0x0C208060 (USER_RW_UNCACHE) to
#      0x09408060 (USER_CDRAM_RW), and the engine's own allocator wrapper 0:0x4C768
#      already rounds CDRAM requests up to 256 KiB (0:0x4C792), so no size line
#      changes and the free path is by memblock UID.  Main then reads 218.1 / 212.1 /
#      216.1 MiB and the video pool 18.0 / 34.0 / 50.0 of 128.  It is a GPU-only
#      surface, so CDRAM is the faster home for it in any case, and at "none" the
#      line re-emits the stock bytes.
#
# NOT A NO-OP AT "none": @FB at 960x544 is byte-identical to the stock game, but @MSAA
#      at "none" is NOT.  Four of its lines rewrite srlib's alternate-slot fragment
#      programs from their stock modes 1 and 2 to 0 (0:0x240B6 and 0:0x2413E were
#      "movs r3,#1", 0:0x240DE and 0:0x24166 were "movs r3,#2").  Mode 0 is the mode
#      of both render targets at that setting, so the slots then agree with the target
#      instead of disagreeing with it, and srlib never begins a scene of its own - but
#      it is a changed byte, not a restored one.  Leave @MSAA off to run stock.
#
# Known limitations / not shipped:
# - @FPS not achieved: menus and map are already 60 FPS and frame-locked, battles are
#        frame-locked at 30 with no timestep constant to patch.
# - The dump contained no runtime records, so every value below was traced statically.
#   @MSAA has since been run on hardware and boots and plays at 4x with the atlas-depth
#   move (0:0x5E646) in place. @IB has not been run on this title; Super Robot Wars X's
#   identical block has, at 960x544. The display render target (0:0x4CB58) and the atlas
#   (0:0x5E6AE) both ignore sceGxmCreateRenderTarget's return value, so a mode the
#   driver refuses is a crash, not a fallback.  See the report.
