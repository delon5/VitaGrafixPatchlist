# The Legend of Heroes: Sora no Kiseki FC Evolution [JP]
#
# Engine VS2010_Hachi_Vita_Shipping (Chara-Ani "Hachi" engine, same design as Ao no
# Kiseki Evolution PCSG00246), module NID 0xAFEE3A2C. Offsets are seg0 offsets of that build.
#
# @FPS construction (the game paces on the display queue, 30 FPS natively):
#  - vcount: the frame flip stores mode 2 in the display-queue entry; the callback passes it
#    to sceDisplayWaitSetFrameBufMultiCB (skipped when <= 1). movs r3, #2 -> vblank.
#  - clock retiming: the game clock advances 33/33/34 ms per logic step (three steps = 100 ms)
#    in the tick (fn 0xD764C) and in the restore-and-tick (fn 0xD7784). The four movs
#    immediates become 17/17/16 ms at FPS=60 (three steps = 50 ms = real time) and re-encode
#    the original bytes at 30/20. The clock speed multiplier (clock+0x18) is not touched, so
#    everything that reads the clock (field, battle simulation, event scripts, ms timers)
#    keeps real time.
#  - steps decision (fn 0x12F788): n = int((ratio + 0.25) * 2), ratio = clamp(30/FPS, 0.5, 2)
#    -> at 60 the constants become 0.125 / 4.0 (the same decision applied to 60/FPS) and the
#    final cmp #4; bne becomes blt so n >= 4 gives 2 steps; at 30/20 the constants are the
#    originals and the native ratio 1.5 at 20 FPS keeps alternating 1/2 steps.
#  - key repeat (fn 0x93618, runs once per logic step): the 14-step initial delay and 3-step
#    repeat of the twelve direction/analog counters are doubled at 60 (raw words with the
#    same instruction, only the immediate changes).
# Known limitations at 60 FPS (integer per-step/per-frame counters that cannot be
# re-expressed; all cosmetic or timeouts, none drives movement, physics or script waits):
#  battle command UI idle timers of 150 steps (fns 0xD09E/0xDD1A/0xE2E2/0xFB5C, +0xd82),
#  the 150-step battle menu idle timers (+0x266 in fns 0x756F6/0x78156/0x7B28C), the 300-frame
#  battle message timeout (fn 0x88DE), the 120-frame voice wait (fn 0xFB5C, +0xd7e), the
#  60-step post-load timer of the field loop (fn 0x8B116, obj+0xc0) and the ~20-frame battle
#  intro fade (game+0xc0e74) all elapse in half the time. Details in PCSG00488.report.md.
#
# @MSAA construction and why it needs a memory line:
#  The engine has its own MSAA path - fn 0x12D5F4 takes the mode as a parameter and sizes
#  the display depth from it (0x1FE000 / 0x3FC000 / 0x7F8000 bytes at stride 960/960/1920).
#  Its only caller passes 0, so one line switches the whole display path.
#  The first build of this option CRASHED at 4x, and the cause was memory, not rendering.
#  The engine takes three memblocks at boot and sub-allocates everything itself. GXM
#  "heap 1" is one USER_RW_UNCACHE block of 14,680,064 bytes (movs.w r2,#0xE00000 at
#  0:0x6B18A), and the eight fixed boot allocations inside it already total 14,557,184
#  bytes - 99.16 % full, 122,880 bytes spare - before multisampling is touched. The
#  display depth is one of those eight, so 2x needs 16,646,144 bytes (1,966,080 short)
#  and 4x needs 20,824,064 (6,144,000 short). The allocation that actually returns 0 at
#  4x is the 8 MiB frame scratch immediately after it (0:0x12D956); its result is handed
#  to four sub-arena constructors with no NULL test, so the first GPU write faults.
#  0:0x12D6F0 is the fix: it selects the heap the display depth comes from, and at 2x/4x
#  it now picks heap 0 - the 96 MiB CDRAM arena, which holds about 10 MiB of identified
#  content. Heap 1 then holds a constant 12,468,224 of 14,680,064 bytes (84.9 %) at every
#  setting, with 2,211,840 spare, and the depth buffer ends up in the pool it belongs in:
#  it is written per pixel per frame, so CDRAM is faster for it as well as safer. The
#  arena is sub-allocated by the engine, not the kernel, so the 256 KiB CDRAM granularity
#  does not apply and no size line is needed. At "none" the line re-emits the stock byte.
#  CONFIRMED ON HARDWARE: with 0:0x12D6F0 in place the game boots and runs at @MSAA = 4x, the
#  setting that previously crashed. The arithmetic above is therefore not just self-consistent,
#  it is the right explanation: the failure was uncached-arena capacity, and moving one
#  allocation out of that arena resolves it. 2x was not separately re-tested and does not need
#  to be - it asks for strictly less of heap 1 than 4x does, and heap 1 is now constant anyway.
#

# The engine already has a native MSAA path in the display init fn 0x12D5F4: its r2 parameter ([sp+0x50])
# drives the colour surface's scaleMode (lr = r2 != 0 at 0x12D68A-0x12D692, passed as r3 to the
# sceGxmColorSurfaceInit at 0x12D6BC) and the display depth surface's memory and strideInSamples
# (0x12D6DE/0x12D6E6/0x12D6EA and 0x12D792/0x12D79E, size = r1 << 2 at 0x12D6EE) - 0x1FE000 bytes at
# stride 960, 0x3FC000 at 960, 0x7F8000 at 1920 for none/2x/4x - twice the D16 (format 0x02444000, two
# bytes per sample) minimum in each mode. The only caller passes 0: movs r2, #0 -> msaa covers both.

# display depth surface heap selector (alloc(heap, align, size), fn 0x13B37A): movs r0,#1 picks GXM

# render-to-texture depth surface (sceGxmDepthStencilSurfaceInit at 0x12DB52, format D16 0x02444000):
# movs.w r2, #131072 is the allocation passed to 0x12DB2E (256*256*2 = the exact D16 minimum) and

0:0x12DB2A t2_mov(1, 2, 131072 * pow(2, msaa))

# generic render-texture depth surface (fn 0x111922, call 0x111AF2, callers 0x12DCA6/0x137C8A/0x137F04).
# Both parameters are computed in registers but each has its own instruction: the allocation size is
# lsls r1, r1, #1 at 0x111AD0 over align(w,32)*align(h,32) (halfword 0x0049, imm5 at bits 10:6), so
# #(1 + msaa) gives x2/x4; strideInSamples is the separate 16-bit adds r3, r4, #0 at 0x111AE8 (0x1C23),
# four instructions after the mul at 0x111AB8 and after the allocation call at 0x111AD4, so replacing it
# with lsls r3, r4, #1 (0x0063) doubles the stride for 4x only and never touches r4 or the mul. r3's old
# value is dead (consumed by the bics.w r1, r3, #31 at 0x111AB4), r4 is not read again, and no flags are
# consumed before the blx at 0x111AF2. At msaa 0 and 1 the line re-encodes the original bytes.
0:0x111AD0 uint16(0x0049 + (msaa << 6))
0:0x111AE8 uint16(0x1C23 - (0x1BC0 * (msaa >> 1)))

# every fragment program in the process carries the same multisampleMode as every render target.
0:0x1393FC t1_mov(3, msaa)
